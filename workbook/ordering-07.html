Device vs Normal Memory

Case 7 of 10 · AWCACHE changes what a response means and what may be reordered
—

0 Background read this first — context before mechanics

Every ordering rule so far has been about IDs and channels. This case is about a different lever entirely: the memory attributes that tell the system how much freedom it has to buffer, merge and reorder your accesses.

What AWCACHE encodes

Four bits, and the two that matter most for ordering are the low pair:

BitNameEffect when set
[0]BufferableAn intermediate agent may return the response on the slave's behalf and complete the write later
[1]Modifiable / CacheableThe system may change the transaction — split it, merge it, widen it, or issue a different number of bursts
[2]Read-allocateHint that a cache may allocate on a read miss
[3]Write-allocateHint that a cache may allocate on a write miss

The Modifiable bit is the one people underestimate. When it is clear, the transaction that reaches the slave must have the same address, size, burst type and length the master issued. When it is set, the system may combine two writes into one, split a burst, or widen an access — none of which is acceptable for a peripheral register.

// Device, non-bufferable — AWCACHE = 4'b0000
BRESP means: the write reached the endpoint
transaction reaches slave exactly as issued

// Normal, bufferable — AWCACHE = 4'b0011
BRESP means: some agent took responsibility
transaction may be merged, split or widened

The performance consequence

Device access is serialised

With non-bufferable attributes, each write must reach the peripheral before its response, so a master issuing dependent device writes pays full round-trip latency on every one. Normal bufferable writes pipeline freely and complete at buffer speed.

In the timing diagram for this case, two device writes take six cycles while two normal writes issue back to back in two. That ratio is not an artefact — it is the cost of the guarantee, and it is why marking everything as device "to be safe" is a serious performance mistake.

Choosing correctly

Device attributes are required when the access has side effects or when the endpoint state matters immediately: peripheral control and status registers, FIFO ports, doorbells, anything where a merge or a widened access would touch neighbouring registers.

Normal attributes belong on ordinary memory: buffers, stacks, heaps, framebuffers. There the system is free to optimise because no address has meaning beyond the bytes it holds.

The bug this creates

Marking a peripheral region as normal, bufferable memory is a classic bring-up error. Writes appear to succeed — BRESP=OKAY arrives promptly from a write buffer — but the peripheral has not seen them yet. Software then writes a control register and immediately reads a status register expecting the effect, and gets pre-write state. Worse, with the Modifiable bit set, the interconnect may merge two adjacent register writes into one wider access, writing a register the software never touched.

The symptom is a peripheral that "sometimes ignores configuration", and the cause is one field in a page table entry.
