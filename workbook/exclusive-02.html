Contention — One Master Loses

Case 2 of 8 · Two masters race, the monitor kills one reservation, nobody corrupts anything
—

0 Background read this first — context before mechanics

The success path shows the mechanism working. This case shows it doing its actual job: two masters race for the same lock, one wins, and the loser is told clearly enough that it can recover.

The sequence

Both cores issue exclusive reads and both receive EXOKAY. That is not a contradiction — the monitor can hold a reservation for each ID simultaneously. Both see the lock free, and both decide to take it.

C0 excl read → EXOKAY, reservation set for ID 3
C1 excl read → EXOKAY, reservation set for ID 8
// both reservations valid at once — legal

C1 excl write → EXOKAY — write performed, C0's reservation killed
C0 excl write → OKAY — reservation gone, write NOT performed

Why the loser's write does nothing

The critical property

A failed exclusive write is a no-op. Memory is left exactly as if the losing master had never attempted it. That is what makes retry safe — every iteration either takes full effect or none.

Contrast with plain writes, where the loser's write would have landed on top of the winner's and destroyed it. The lost-update problem is not that two masters raced; it is that both writes took effect. Exclusive access does not prevent the race — it ensures only one write survives it.

Reading the outcome correctly

Core 0 receives BRESP=OKAY. Nothing failed in the sense of an error: the bus worked, the slave worked, no protocol rule was broken. What happened is that the reservation was invalidated, so the conditional write was declined.

A driver that checks only for SLVERR and DECERR sees no error and concludes the write succeeded. It then believes it holds a lock that core 1 actually holds. This single misreading is the most common exclusive-access bug in real drivers.

Which master wins

Whichever exclusive write reaches the monitor first. That depends on arbitration, interconnect latency, and how quickly each core computed its new value — none of which is under software control and none of which is fair by construction.

ConsequenceWhat it means in practice
No fairness guaranteeA master can lose repeatedly. Nothing in AXI4 prevents starvation
Contention costs iterationsUnder heavy contention most attempts fail and the retry loop dominates
Backoff helpsSoftware often adds a delay after a failure to reduce collision probability
Design out contentionPer-core locks, sharding, or lock-free structures are usually better than a heavily contended single lock

What to look for in a trace

Two reservations set, one EXOKAY write, one OKAY write, and memory holding only the winner's value. If you instead see both writes take effect, exclusive access is not actually engaged — check that AWLOCK is asserted and that RRESP was EXOKAY on the reads.
