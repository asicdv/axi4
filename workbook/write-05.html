Same-ID Write Ordering

Case 5 of 10 · Shared ID forces both data and responses into order
—

0 Background read this first — context before mechanics

Give two writes the same AWID and you constrain both channels that could otherwise vary: the B responses must come back in address order, and — because AXI4 already orders all write data — the memory effects land in order too.

What the shared ID adds

Write data was already strictly ordered regardless of ID, so sharing an ID changes nothing on the W channel. What it adds is the response guarantee: BID=3 for the first transaction must be delivered before BID=3 for the second.

// different IDs
W : forced order B : any order

// same ID
W : forced order B : forced order

That response ordering is what a master actually uses to reason about completion. If it knows response A precedes response B, then observing B tells it A has also completed — one check instead of tracking both.

Where it matters

SequenceWhy order is required
Payload then flagWrite the data buffer, then set the "ready" flag another agent polls. If the flag lands first, the reader sees stale payload behind a valid flag
Descriptor then doorbellWrite a DMA descriptor, then ring the doorbell register that starts the engine. Reversed, the engine reads a descriptor that is not yet written
Configure then enableSet a peripheral's parameters, then set its enable bit. Enabling before configuration can start hardware in an undefined state
Log then commitJournalling structures where the record must be durable before the pointer advances
What it does not give you

Same-ID ordering is a guarantee among writes. It says nothing about a read that follows — AR is an independent channel and no cross-channel ordering exists. A read issued after a same-ID write can still observe the pre-write value.

The cost, and the usual mistake

Every transaction sharing an ID is serialised against every other transaction with that ID, on the response path. A master that routes all its writes through a single ID for safety has given up response reordering entirely — one slow write to a distant peripheral now delays the completion reporting of every subsequent write, including ones to fast local memory.

The correct discipline is the same as on the read side: share an ID exactly where a dependency exists, and use distinct IDs everywhere else. ID assignment expresses your dependency graph. Collapsing it to one ID does not make the design safer in any way that matters — write data was already ordered — it only makes it slower.

Ordering is not the same as visibility

One subtlety worth carrying into the Ordering topic: the guarantee is that the responses arrive in order and that the writes take effect in order relative to each other. It is not a guarantee about when either becomes visible to another master. With bufferable memory, both writes may still be sitting in an interconnect write buffer when their responses come back. Order between them holds; global visibility is a separate question with a separate answer.
