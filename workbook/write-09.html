Narrow Write

Case 9 of 10 · Lanes shift per beat, and WSTRB makes it self-describing
—

0 Background read this first — context before mechanics

A narrow write moves fewer bytes per beat than the bus can carry, and the active byte lanes walk up the bus word as the burst progresses. Unlike the read case, the write carries an explicit statement of which lanes are live: WSTRB.

The lane progression

Which lanes are active follows from the beat address, exactly as on the read side:

// AWADDR=0x1002, AWSIZE=1 (2 bytes), 64-bit bus
beat 0 @ 0x1002 → offset 2 → lanes [3:2] → WSTRB=8'b0000_1100
beat 1 @ 0x1004 → offset 4 → lanes [5:4] → WSTRB=8'b0011_0000
beat 2 @ 0x1006 → offset 6 → lanes [7:6] → WSTRB=8'b1100_0000
beat 3 @ 0x1008 → offset 0 → lanes [1:0] → WSTRB=8'b0000_0011

The advantage over reads

Self-describing

On a narrow read the master must compute which lanes to sample, and a mistake is invisible to every checker on the bus. On a narrow write the strobes state the answer explicitly — a monitor can verify that WSTRB matches what AWADDR and AWSIZE imply, and flag a mismatch immediately.

That makes narrow writes considerably easier to verify than narrow reads. If you are writing a protocol checker, the strobe-versus-address consistency check is one of the highest-value assertions you can add: it catches lane computation bugs at the moment they occur rather than downstream where they look like data corruption.

Where narrow writes come from

SourceWhy the access is narrow
Sub-word storeSTRB, STRH — the architectural access size is part of the instruction and must not be widened
Narrow peripheral registerA 16-bit control register on a 64-bit fabric implements only two lanes
Legacy IP behind a bridgeA 32-bit device on a 128-bit interconnect; the bridge issues at the device's width
Unaligned store fixupAn access straddling a bus word is split into pieces, each within one word

The efficiency question

This transfer uses two of eight lanes per beat — 25% utilisation. Four beats occupy the write data channel to move eight bytes that one wide beat could carry. When the access width is architecturally required, that is simply the cost. When it is not, sustained narrow traffic from a high-bandwidth master is a finding worth chasing: it usually means a width-conversion bridge is missing or a bus-width parameter is wrong, and correcting it can multiply throughput.

The bug that hides

A master that emits a fixed strobe pattern on every beat — the same lanes each time — gets beat 0 right whenever the start address is bus-aligned, and gets every subsequent beat wrong. Tests written with aligned addresses pass completely. The failure appears in the field the first time software stores to an offset within a bus word, and it presents as data landing at the wrong byte position rather than as anything recognisably protocol-related.
