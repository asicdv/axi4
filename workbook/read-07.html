FIXED Burst

Case 7 of 8 · Every beat reads the same address — draining a hardware FIFO
—

0 Background read this first — context before mechanics

FIXED is the burst type that does not increment. Every beat targets the identical address, and each beat returns different data. That only makes sense if the thing being read has internal state — which is exactly what it is for.

The mental model

A memory-mapped FIFO occupies one address. Reading that address pops the oldest entry and advances an internal pointer. The address is a port, not a location. Reading it four times drains four entries; reading four consecutive addresses instead would touch four unrelated registers.

// UART receive FIFO mapped at 0x5000, holding 'H','e','l','p'

FIXED, 4 beats → 0x5000, 0x5000, 0x5000, 0x5000
returns 'H' 'e' 'l' 'p' ✓

INCR, 4 beats → 0x5000, 0x5001, 0x5002, 0x5003
returns 'H' + three unrelated registers ✗

The INCR version is not merely inefficient — it is wrong, and on a peripheral with read-sensitive registers it is destructive. Reading 0x5001 might clear an interrupt status, acknowledge an error, or pop a second FIFO. The burst type here encodes a semantic fact about the target, not a performance preference.

Where FIXED appears

TargetWhat each beat does
UART / SPI RX FIFOPops one received byte per beat. A short FIXED burst drains the FIFO with a single address phase instead of one per byte
Ethernet MAC RX bufferSome MACs expose the packet buffer through a single data port with an auto-incrementing internal pointer
Hardware queue / mailboxReading the head register dequeues an entry and presents the next
Entropy sourceEach read of the RNG output register produces a fresh sample
Constraint worth knowing

ARLEN+1 for a FIXED burst is limited to 16 beats. There is no reason to go further — you are draining a small hardware structure, not streaming memory — and the limit keeps a stalled peripheral from monopolising the data channel indefinitely.

Why the slave must be built for it

A FIXED read is only correct if the slave's read has a side effect. That is unusual: most slaves are memories, where reading the same address four times returns the same value four times. Issuing FIXED to an ordinary memory is legal and returns four copies of one word — pointless, but harmless.

The reverse mistake is the dangerous one. Issuing INCR to a FIFO-style slave silently reads neighbouring registers, and because those reads have their own side effects, the damage is not confined to the data you got back. This is why device regions are marked non-cacheable and non-bufferable: it prevents any layer of the system from speculatively fetching addresses the software never asked for.

The debugging signature

FIXED bugs have a characteristic shape. Data comes back looking structurally plausible — the right number of beats, no error response — but the content is a mixture of the value you wanted and unrelated register contents. Meanwhile some other part of the peripheral changes state for no reason anyone can explain, because a status register got read as a side effect. If you are chasing "this peripheral behaves oddly when we drain its FIFO", check ARBURST first.
