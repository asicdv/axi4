False Sharing

Case 7 of 8 · An unrelated variable in the same granule breaks your reservation
—

0 Background read this first — context before mechanics

Monitors do not track individual addresses. They track aligned regions — typically a cache line. A write anywhere in that region invalidates the reservation, even to a variable that has nothing to do with yours.

Why granularity exists

Tracking every byte address a master might reserve would require storage proportional to the address space. Real monitors keep a small table of {region, ID, valid} entries and compare masked addresses, which reduces the comparison to a few gates. The price is that the region is coarser than the variable.

lock @ 0x5040 // the variable you reserved
counter @ 0x5050 // 16 bytes away, entirely unrelated

monitor granule = 64B → watches 0x5040–0x507F
write to 0x5050 → reservation dies

The lock was never written. It still holds FREE throughout. The exclusive write fails anyway.

Why this is correct behaviour

Conservative, not broken

The monitor errs toward invalidating. A false failure costs a retry; a missed invalidation would corrupt data. Given a choice, the safe direction is obvious — so monitors are deliberately over-eager.

That framing matters when you find this. Nothing is malfunctioning. The hardware is trading precision for cost in the direction that cannot produce wrong answers.

The cost

Retries that contention alone would not explain. A lock with a single user and no competing lock traffic can still fail repeatedly if a busy counter shares its cache line. Throughput on the lock collapses while the profiler shows no lock contention at all — because there is none.

FixHow it works
Cache-line alignmentAlign each synchronisation object to the granule and pad it to fill one. The Linux kernel does exactly this for spinlocks
Separate the hot dataMove frequently written counters and statistics out of the same line as any lock
Dedicated regionPlace synchronisation objects together in their own area, away from ordinary data
Padding structuresInsert filler so that per-core structures each occupy whole lines

Recognising it

The distinguishing signature is failure without contention. Under true contention you will see multiple masters issuing exclusive reads to the same address; under false sharing you see one exclusive user and a stream of ordinary writes to nearby addresses.

Look at the addresses, not just the failure rate. Two addresses that differ only in their low six bits share a 64-byte granule, and that is the whole diagnosis.
