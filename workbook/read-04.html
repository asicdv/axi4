Same-ID Ordering

Case 4 of 8 · Two reads share an ID — the protocol forbids overtaking
—

0 Background read this first — context before mechanics

This is the mirror of the previous case, and the pair is best studied together. Identical stimulus, one field changed, and the guarantee inverts completely. That single field is ARID.

What sharing an ID buys you

When two reads carry the same ID, AXI4 guarantees their responses appear on the R channel in the order the addresses were accepted. Read A's beats — all of them, ending with RLAST — must complete before any beat of Read B appears. The slave may fetch in whatever order it pleases internally; what it may not do is let B's data overtake A's on the bus.

That guarantee is what lets a master do something very useful: issue several dependent reads back to back without waiting for any of them, and still consume the results in a known order.

// serialise at the master: wait for each RLAST before next ARVALID
read A → 40 cyc, then read B → 40 cyc = 80 cycles

// pipeline with a shared ID: both addresses out immediately
A and B in flight together, ordered return = ~44 cycles

// same ordering guarantee, half the time

This is the point that gets missed. Same-ID does not mean serialised. The address channel still pipelines; the slave may still have both fetches running concurrently. Only the return order is constrained.

When you need it

SituationWhy order matters
Status then dataSoftware reads a status register, then a data register whose meaning depends on that status. Seeing them out of order yields a coherent-looking but wrong interpretation
Descriptor chainA DMA engine reads descriptor N, which contains the pointer to N+1. The dependency is real; ordering is not optional
Producer/consumer flagRead the flag, then the payload it guards. Reordered, you read payload that was not yet valid when the flag was checked
Peripheral FIFO drainSuccessive reads pop successive entries. Out-of-order return would scramble the stream
Where the cost lands

Sharing an ID couples transactions that may have nothing to do with each other. If a master funnels all its traffic through one ID for safety, a single slow access blocks every subsequent response — you have rebuilt in-order return and thrown away the reason AXI has IDs. ID assignment is a real design decision, not a default.

The subtlety worth carrying forward

Same-ID ordering is a guarantee about the read channel only. It says nothing about reads versus writes, and nothing about when memory actually changes. A read that follows a write to the same address, even with matching IDs, is not ordered against that write — the AR and AW channels are independent and there is no cross-channel guarantee. That case is the RAW hazard, and it is the single most common source of real ordering bugs in SoCs. You will meet it in the Ordering topic; note now that this case does not solve it.
